## Rationale

Executor failed a discovery / identify-all task (3.1% record Jaccard; 4 of 21 fraud payments recovered; 107 false positives). The Executor did enumerate the signal families v0004 added (PMF / DFP sharing, basket reuse, amount mismatch, observed-vs-store location, impossible travel, observed-vs-home location) and correctly observed that all the discrete-identifier signals returned zero matches — but then adopted the one signal that *did* produce matches (continuous geographic distance: device near home, far from claimed store) as the answer, sweeping the threshold to 111 records without verifying that the matched set shared any exact identifier. The actual cohort was identified by an authentication-state invariant in the schema's `three_ds_*` columns (a column family the Executor never queried, even though it sits next to `observed_lat`/`observed_lon` in the same `payments` table per `bin-help/sqlite_schema.txt`, and `/docs/payments/3ds.md` documents the legitimate state transitions a `paid` row must come through). Two new failure modes to address on top of v0004's discipline: (a) the schema-driven column sweep is implicit, so authentication / workflow-state columns whose name does not contain 'fraud' get skipped; (b) the existing 'enumerate every signal' rule does not distinguish a discrete-identifier signal (likely the cohort) from a continuous-threshold signal (likely noise), so the Executor treated 'first non-empty signal' as 'the answer'. Fix: add an Authentication / workflow-state-invariants row to the signal-families table that points at `three_ds_status` / `three_ds_failure_reason` / `three_ds_attempts` and the topic doc that governs them; add rule 3 (schema-driven column sweep — open `bin-help/sqlite_schema.txt`, copy the full column list of the in-scope table, consider each column, read the topic doc for any nullable status / workflow column); add rule 4 (discrete identifier > fuzzy threshold — prefer signals whose match set is identified by a shared exact value; ablate any threshold-only signal and require either a sharp count break or a discrete shared property before treating it as the cohort); extend rule 6 to note that 'one hit' still implies the records share at least one discrete identifier; extend the coverage check to require recording the full considered-column list and per-signal exact-identifier-vs-threshold status; add a 'low precision vs low recall' framing at the section opening; add three anti-patterns (adopting the first non-empty signal as the answer; skipping authentication-/workflow-state columns because the name does not contain 'fraud'; submitting a threshold-only candidate set as the cohort); update the 'For a discovery / identify-all task, every /proc/... record the answer marks' bullet to mention precision as well as recall. Generalises across any /proc/<family> with a workflow-state column governed by a topic doc.
